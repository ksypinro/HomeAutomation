04 · Comparative runtime analysis

Three paths, one result contract.

The evaluation harness compares a baseline DAG, that DAG with a deterministic Tier‑1 automation action path, and a bounded verifier loop. They accept the same request and return the same result type—but their cost, safety coverage, and maturity differ.

graphgraphWithTier1verifierLoop

First, name them correctly

The word “orchestrator” is used at two levels in this repository.

Runtime modes: two

OrchestrationMode contains graph and verifierLoop. HomeCommandOrchestrator branches on this value after root routing.

Evaluation arms: three

OrchestrationArm adds graphWithTier1. It is still graph mode, but its registry wires automation actions to AutomationActionMiniPipeline.

Shared input and output

All arms receive text, executeLowRiskCommands, and SmartThings creation options through CommandRequest. They stream pipeline events and terminate with HomeAutomationResolverResult.

Shared ingress

Even verifier-loop mode currently pays this front-end cost before its own deterministic Stage 0.

The three execution paths

Each summary follows control flow, calls, output, resilience, and the critical latency shape.

01

Runtime mode · production default

Legacy graph / DAG

Algorithm. GraphPlanner selects a static operation-specific DAG. GraphScheduler validates it, repeatedly launches every dependency-ready node, commits typed patches as tasks finish, and stops on terminal context or an approved transition.

Direct-command topology. Three parallel NLU nodes → barrier → four parallel evidence/candidate nodes → eleven-node sequential judge/rank/hydrate/capability/draft/safety/execution spine. With models unavailable, a deterministic fallback graph runs.

Automation topology. Seven outer stages are sequential. The fan-out node internally schedules trigger, actions, and conditions with a six-task cap, condition batching, clarification cancellation, session pooling, and speculative segmentation/compilation.

Reachable model tools. analyzeOperationSemantics; capability device-detail/all-capability tools; draft device search, command inspection, candidate hydration, and optional current-state tool.

  • Best qualities: validated static topology, typed data isolation, real parallel waves, circuit breakers, graph-level timeouts/retries, checkpoints, rich traces, and mature fail-closed gates.
  • Main cost: a model-first front end and a long sequential critical path; automation actions can each repeat a full direct-command subgraph.
  • Output: context-derived direct result, automation result, clarification, confirmation, or unsupported terminal state.
02

Graph configuration · evaluation arm

Graph + Automation Tier‑1

Algorithm. The outer scheduler and graphs are unchanged. Only each automation action branch changes: deterministic envelope → candidate hydration → confidence gate → optional capability specialist → structural draft → deterministic validation.

Call budget. A confident action uses zero FM calls. If the minimum envelope-field confidence is below 0.78, the pipeline makes at most one capability-resolution model call with two canonical tools.

Parallelism. Actions still run inside the six-way component fan-out and results are restored to declaration order. The resolver’s separate two-action cap applies to resolveAll, not the active single-action fan-out calls.

  • Best qualities: large multi-action latency reduction with the same outer graph, validation, compiler, and reversible feature flag.
  • Main limitation: a low confidence in any field calls the capability specialist even when target, intent, room, or risk is the weak field.
  • Resilience gap: direct mini-pipeline worker calls bypass graph-level specialist timeouts, retries, and circuit breakers; only the 300-second outer fan-out timeout remains.
03

Runtime mode · bounded experimental path

Deterministic verifier loop

Algorithm. Build a field-level DraftEnvelope deterministically; pre-repair zero-confidence fields; verify through one reusable constrained session; route disputes to specialists; run disjoint repairs concurrently; merge in stable order; latch repaired fields; re-verify with a delta prompt.

Hard bounds. Three verifier iterations, three repair groups per iteration, six disputes per verdict, field latching, strict progress, and escalation on verifier failure, no progress, repair latch, or iteration cap.

Calls. The verifier has no tools. Target/risk/operation repairs are deterministic; capability repair can use two canonical tools; fragment NLU performs two model responses. Escalation makes the full graph tool set reachable.

  • Best qualities: low expected model-call count, typed provenance/confidence, constrained verdicts, targeted parallel repairs, delta prompts, and a safe legacy escalation concept.
  • Coverage gap: trigger, condition, segmentation, and holistic repair dispatch currently return nil.
  • Safety gap: accepted loop outputs return through LoopResultBridge before the graph’s mandatory direct-command/automation finalization gates.

Improvement review

Prioritized from release blockers to latency refinements. These are findings, not changes already made.

P0 · Safety and correctness

P0.1 · shared finalizer

Run one mandatory post-draft gate chain for every arm

Loop acceptance currently bypasses safety validation, parameter validation, confirmation policy, execution planning, automation validation, and requested SmartThings creation. Create a common finalization subgraph and never let an arm return a mutation-capable result before it.

Evidence: HomeCommandOrchestrator.swift:408–425; LoopResultBridge.swift:47–136.
P0.2 · verdict invariants

Normalize acceptance, clarification, and risk

Accept only when there are no disputes, no clarification request, and no understated risk. Convert riskUnderstated to a risk dispute and check it before the accepted fast path.

Evidence: DraftVerdict.swift:171–178; VerifierLoopOrchestrator.swift:141–166.
P0.3 · repair truth

Latch only fields that were actually repaired

Group repair steps by specialist and component scope, return written field IDs from each specialist, and latch only successful writes. Today one multi-action specialist result can repair one field while the loop latches several.

Evidence: RepairPlanner.swift:55–89; RepairSpecialistRegistry.swift:28–68.
P0.4 · specialist completeness

Make scheduled repairs real

Implement fragment-NLU merge, hydrate capability-repair candidates, and add trigger/condition/segmentation specialists—or stop scheduling those paths. Rebuild the envelope when operation repair changes command versus automation shape.

Evidence: EnvelopeMerger.swift:55–74,238–246; RepairSpecialistRegistry.swift:87–123.

P0 · Measurement integrity

P0.5 · call accounting

Count model calls where they happen

Use a run-scoped counter inside FoundationModelCallRecorder. Stage-status inference counts non-model nodes, misses threshold skips and repeated attempts, omits automation/loop early returns, and can report zero for real work.

Evidence: OrchestratorMetrics.swift:518–556.
P0.6 · comparable clocks

Measure true gate wait and one end-to-end window

The comparison labels graph-node queue duration (seconds) as FM queue milliseconds. Read actual gate telemetry, include root routing in every arm, identify cold/warm/thermal runs, and counterbalance live arm order.

Evidence: OrchestrationComparisonRunner.swift:273–275; current loop/automation duration windows differ.

P1 · Latency and resilience

P1.1 · loop ingress

Remove duplicate model routing in loop mode

Use deterministic operation detection for loop mode and let the verifier dispute it. Pass the context’s memory hints into the deterministic envelope. Add the same short soft deadline to model-backed root routing when the graph path needs it.

Removes one hot-path FM call and restores follow-up context.
P1.2 · reuse escalation

Seed a minimal escalation graph

Call and extend LoopResultBridge.seedContext, then skip already-valid stages through an escalation-specific DAG. Current loop escalation simply falls through and repeats target, capability, and draft work.

Evidence: LoopResultBridge.swift:31–43; HomeCommandOrchestrator.swift:384–390.
P1.3 · stop early

Cancel sibling work on terminal outcomes

When clarification, unsupported, or terminal failure is known, cancel already-running siblings that are not required cleanup. The scheduler currently stops launching new nodes but still waits for the task group.

Evidence: GraphScheduler.swift:284–321.
P1.4 · graph semantics

Honor required nodes and manifest retry policy

A missing/open-circuit required non-safety node should fail or fall back—not be marked complete. Replace ambiguous hard-coded retry counts with manifest maxAttempts semantics and cancel the losing timeout sleeper.

Evidence: GraphNodeExecutionLoop.swift:165–233; OrchestratorPolicyEngine.swift:32–39,124–134.
P1.5 · Tier‑1 specialists

Escalate the field that is actually weak

Target weakness should call target resolution; intent/slots should call fragment NLU; capability/command should call the capability worker; risk should call deterministic risk policy. Apply target changes and wrap each specialist in timeout/circuit telemetry.

The injected fragment-NLU worker is currently unused by the mini-pipeline.
P1.6 · speculation

Patch only the plan diff

Reuse Wave‑1 outcomes for unchanged component IDs and resolve only added or changed trigger/action/condition work. Current code computes a diff, then reruns the entire refined plan.

Evidence: AutomationComponentFanOutRunner.swift:129–161.
P1.7 · scarce model gate

Activate real priority and aging

All recorder call sites currently use the default interactive lane, so the documented two-lane scheduler is inert. Label long draft/action work as pipeline, keep short verifier/trigger/condition calls interactive, then add aging to prevent starvation.

Evidence: FoundationModelGate.swift; no production .pipeline call site.
P1.8 · sessions

Prewarm correctly and isolate state

Constructing a LanguageModelSession is not Apple’s prewarm(promptPrefix:). Sessions accumulate transcript, so do not pool them across unrelated requests; reuse only within a run or recreate from an immutable prefix, and discard failed sessions.

Platform constraints are sourced on the latency playbook page.

Recommended rollout posture

Safety parity and trustworthy measurement come before a default-mode decision.

Keep graph as the reference

Repair required-node, retry, cancellation, priority, and telemetry semantics while preserving it as the broadest-coverage escalation path.

Promote Tier‑1 first

After field-specific escalation and specialist timeout/circuit integration, it offers the lowest-risk large reduction for multi-action automations.

Shadow the verifier loop

Do not make it default until the common final safety chain, complete automation specialists, correct repair merging/latching, seeded escalation, memory handling, and live call telemetry all pass.

Add adaptive selection only after measurement

The next page proposes a fourth orchestrator that routes among the three existing arms and schedules their frontier more intelligently.
