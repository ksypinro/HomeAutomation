The key contract

A graph agent reads a snapshot of ResolutionContext, receives a typed input through ContextualHomeAgent, and returns a ResolutionContextPatch. The scheduler—not the agent—commits shared state.

How one agent works

The same five-part lifecycle applies whether the implementation uses a model, RAG, a registry, or only deterministic rules.

1. Input construction

A contextual adapter reads only the fields needed from the latest context snapshot. Missing mandatory prerequisites become a structured input error before the agent starts.

2. Narrow processing

The typed run(input, context) method performs one responsibility. Model-backed workers usually start with deterministic hints and retain a deterministic fallback.

3. Tool or service calls

Calls may reach Foundation Models, RAG retrieval, the device registry, capability catalogs, SmartThings compilation/creation, or compact model tools. Most safety agents call no model.

4. Typed output & patch

The result is mapped to context keys or typed artifacts. Patches can also request clarification, mark unsupported input, or return a structured failure.

5. Scheduler decision

The graph runtime records timing, updates the circuit breaker, applies retry and fail-closed rules, commits the patch, then recomputes which nodes are ready.

6. Observable outcome

Events stream to the UI while traces, graph timings, FM usage, retrieval reports, loop convergence, and circuit states are collected for evaluation.

About the “three orchestrators”

The evaluation names three arms, but the runtime exposes two top-level modes.

Important naming distinction

graph and verifierLoop are runtime modes. graphWithTier1 is the same graph runtime with useMiniPipeline: true for automation actions. The comparison harness treats all three as separate arms so latency and quality can be measured fairly.
