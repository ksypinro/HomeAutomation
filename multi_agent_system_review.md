# Multi-Agent System (MAS) Architectural Review: HomeAutomation

This document evaluates the `HomeAutomation` orchestrator through the lens of classic and modern Multi-Agent System (MAS) architectures. It focuses on how agents are coordinated, how they exchange data, the strengths of the current implementation, gaps compared to traditional MAS paradigms, and pathways for future refinement.

---

## 1. Architectural Foundations: Current State

The system utilizes a hybrid **Blackboard + Directed Acyclic Graph (DAG) Orchestration** model. 

```
                               ┌─────────────────────────┐
                               │    ResolutionContext    │
                               │      (Blackboard)       │
                               └────────────▲────────────┘
                                            │ (Read / Write Patches)
  ┌─────────────────────────────────────────┼─────────────────────────────────────────┐
  │ Orchestrator Runtime                    │                                         │
  │                                         ▼                                         │
  │  ┌──────────────┐             ┌───────────────────┐             ┌──────────────┐  │
  │  │ GraphPlanner │────────────►│  GraphScheduler   │◄────────────│AgentRegistry │  │
  │  │ (Static DAG) │             │ (Task Group Loop) │             │ (Capabilities│  │
  │  └──────────────┘             └─────────┬─────────┘             └──────────────┘  │
  │                                         │                                         │
  │                      ┌──────────────────┼──────────────────┐                      │
  │                      ▼                  ▼                  ▼                      │
  │              ┌──────────────┐   ┌──────────────┐   ┌──────────────┐               │
  │              │   Agent A    │   │   Agent B    │   │   Agent C    │               │
  │              └──────────────┘   └──────────────┘   └──────────────┘               │
  └───────────────────────────────────────────────────────────────────────────────────┘
```

*   **Registry & Identity:** Agents conform to `AnyHomeAgent`, exposing an `AgentManifest` that declares their identity (`AgentID`), capabilities (`AgentCapability`), consumed/produced keys, priorities, and retry policies.
*   **Coordination (Control Loop):** The `GraphScheduler` drives execution by traversing an `OrchestrationGraph` generated by the `GraphPlanner`. Ready nodes are executed concurrently using Swift's native structured concurrency (`withTaskGroup`).
*   **Communication (Data Flow):** The state is managed via a thread-safe, immutable snapshot (`ResolutionContext`). Agents are functional pipelines: they ingest a snapshot, run their local reasoning, and emit a declarative `ResolutionContextPatch` specifying keys to update.

## 2. Agent Coordination

### What is Done Well
*   **Concurrency & Dependency Resolution:** The `GraphDependencyTracker` computes ready nodes dynamically. Parallel branches (e.g., executing multiple NLU models or retrieving capability knowledge) run concurrently.
*   **Fail-Safe Gates & Resiliency:** Integrated circuit breakers (`AgentCircuitBreaker`) prevent cascading failures, and timeouts are enforced per agent. Mandatory safety gates can abort execution cleanly ("fail-closed" model).
*   **Dynamic Selection by Capability:** Nodes in the DAG can specify a capability requirement (`.byCapability(capability)`) rather than an explicit agent ID, allowing runtime binding to the highest-priority agent supporting that capability.

### Gaps (Compared to Mature MAS)
*   **Static vs. Dynamic Planning:** 
    *   *Current:* The `GraphPlanner` builds the execution graph *up front* based on the detected operation type (e.g., direct command vs. automation creation). 
    *   *Standard MAS:* Classic MAS (like BDI or Contract Net Protocol) features **dynamic planning**. Agents evaluate the goal state, bid on tasks based on utility metrics, and dynamically rewrite the execution plan or recruit sub-agents at runtime.
*   **Lack of Peer-to-Peer Negotiation:** Agents do not converse, negotiate resource allocation, or resolve conflicts directly (e.g., two agents trying to resolve different target devices). All conflicts must be anticipated and handled by subsequent ranking/validation agents.
*   **No Agent Autonomy (Passive Execution):** Agents in this system are reactive function executors. They lack their own run loops, do not proactively monitor system changes, and cannot decide to initiate tasks without scheduler invocation.

## 3. Agent Data Communication

### What is Done Well
*   **Immutability and Thread Safety:** Passing a copy of the read-only `ResolutionContext` prevents race conditions. This is an elegant design pattern for shared-state systems in Swift.
*   **Structured Scopes:** The `ContextScope` enum (e.g., `.root`, `.action(id)`, `.condition(id)`) isolates memory segments when parsing nested arrays of actions or conditions, mitigating cross-talk.

### Gaps (Compared to Mature MAS)
*   **High Blackboard Coupling:**
    *   *Current:* The system relies heavily on a centralized **Blackboard Pattern**. The `ResolutionContext` is a monolith holding concrete properties for almost every specific agent type (e.g., `deviceType`, `slots`, `retrievedCandidates`, `instructionPackage`).
    *   *Impact:* Adding a new agent type often requires updating `ResolutionContext` and `ResolutionContextPatchKey`. This violates the Open-Closed Principle and couples agents to a global domain model.
*   **Unstructured Data Passing:**
    *   *Current:* Loose state values are placed inside `scopedValues` using `AnySendableValue` (a type-erased wrapper). Retrieving them requires string keys and unsafe/fallible runtime downcasting (e.g., `context.scopedValue(for: ScopedContextKeys.validation())`).
    *   *Standard MAS:* Mature MAS uses standard agent communication languages (e.g., **FIPA-ACL**) or a structured, typed message-bus architecture where data schemas are defined at the interface level, not type-erased at the core.

## 4. Key Architectural Evolution Paths

To shift the project toward a more modular, sophisticated MAS, the following structural improvements are recommended:

### A. Transition from Hardcoded State to Semantic Message Passing
Instead of the central `ResolutionContext` knowing about every agent's internal types, the blackboard should transition to a **Key-Value Attribute Space** or a **Semantic Tuple Space**. 
*   **Typed Sub-Contexts:** Slice `ResolutionContext` into protocol-driven facets (e.g., `NLUContext`, `RAGContext`, `SafetyContext`). Agents only receive and mutate their specific slice.
*   **Dynamic Data Contracts:** Agents should define their inputs and outputs strictly via Swift Protocols. The orchestrator maps the output protocol of one agent to the input protocol of the next, removing type erasure.

### B. Reactive Graph Mutation (Dynamic Planning)
Allow agents to mutate the orchestration graph during execution.
*   If the `RiskClassificationAgent` detects a `.critical` risk level, it should be able to dynamically inject a `.safetyValidation` or `.humanApproval` node into the remaining execution queue, even if the graph was originally configured without one.
*   Implement a **re-planning loop** where, if an agent fails and cannot recover, the planner recalculates an alternative path using remaining capabilities.

### C. Formal Agent Protocols & Lifecycle
Decouple agents from direct orchestrator code by defining a formal lifecycle interface:
```swift
protocol AutonomousAgent: Sendable {
    var manifest: AgentManifest { get }
    func canHandle(goal: OrchestrationGoal, context: ResolutionContext) -> Double // Return confidence/bid score
    func execute(context: ResolutionContext) async -> AgentRunResult
}
```
This allows the Orchestrator to route work using a **Contract Net Protocol** (polling agents for capability bids) rather than static registry mapping.

## 5. Summary Evaluation Matrix

| Architectural Dimension | Current Implementation | Mature Multi-Agent System | Recommendation for HomeAutomation |
| :--- | :--- | :--- | :--- |
| **Coordination** | Centralized scheduler traversing a static DAG. | Decentralized or dynamically planned coordination (negotiation/bidding). | Allow NLU/Routing agents to dynamically alter the DAG topology mid-run. |
| **Data Exchange** | Monolithic blackboard (`ResolutionContext`) + type-erased scopes. | Peer-to-peer message passing or decentralized semantic bus. | Refactor blackboard to protocol-based context slices. |
| **Extensibility** | Registry lookup by capability is supported, but updating the state schema requires core changes. | Open, plug-and-play agents specifying semantic inputs/outputs. | Standardize input/output structures using Swift generics instead of `AnySendableValue`. |
| **Resiliency** | Circuit breakers and timeouts per agent node. | Adaptive self-healing and path reconfiguration. | Implement dynamic fallback routing when a breaker opens. |
